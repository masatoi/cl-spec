# cl-spec 反証条件

- 日付: 2026-09-09
- 状態: MVP vertical slice 完成直後、MCP adapter 着手前に記述
- 参照すべき時: §65 のループを一周させた後、および設計の妥当性を問い直すとき

## この文書の目的

cl-spec の大目標は「LLM が Common Lisp のコードを安全に変更するための semantic
feedback loop を成立させること」であり、仕様書 §71 はその達成基準として5つの問いを
挙げている。しかしこの5つは**仮説**である。LLM が実際に必要とする情報がこれで足りて
いるという証拠は、現時点で存在しない。

「有効性」を事前に定義することはできない。測定対象が確率的で、ベースラインが汚染され
やすく、そして何より、どこで役に立たないかを知らないまま指標を決めると測るべきでない
ものを測るからである。

代わりにここでは**反証条件**を定める。「有効か」ではなく「何を観測したら手を止めるか」
を、作る前に書いておく。これは測定装置ではなく、**後から言い訳できなくするための装置**
である。

## 使い方の総則

- 条件が発火したら、まず**対応欄のとおりに動く**。「条件が悪かった」で流さない。
  この文書が機能するのは、書いた人間がそれに従う気があるときだけである。
- 発火は失敗ではない。F7 のように、**発火してほしい**条件もある。
- 条件を後から緩めてよいのは、緩める理由が観測から出たときだけである。作った量が
  惜しいという理由は該当しない。

## F1. ループに人間の翻訳が必要

**否定する主張**: §65 のループが閉じる。

**反証観測**: LLM が MCP の返答を受け取ってから source modification に至るまでの間に、
人間が情報を作り直す・貼り直す・言い換える必要がある。

**確認方法**: 実際の編集タスクを1周させ、人間の介在が「承認」以外に発生した回数を数える。
0 でなければ発火。

**発火時**: ループは閉じていない。MCP のスキーマか、その手前の構造化データの形が誤って
いる。§65 の図を作り直す。

**確認可能時期**: MCP adapter 完成後。

> この条件が最も強い。判断が要らず、二値で、言い訳のしようがない。

---

## F2. 構造化された答えが読まれない

**否定する主張**: §22「構造化された説明データを primary representation とする」、
§38「introspection first」。

**反証観測**: LLM が `describe_symbol` / `explain-data` の返答を得た**後で**、同じ情報を
得るために結局ソースを読んでいる。

**確認方法**: transcript を見て、構造化応答の直後にソース読み取りが続く割合を数える。

**発火時**: 構造化データが情報を置き換えていない。追加コストにしかなっていない。
返す内容が足りないのか、形が使いにくいのかを切り分ける。前者なら §28 の
`describe_symbol` の項目を見直し、後者なら投影の形を見直す。

**確認可能時期**: MCP adapter 完成後。

---

## F3. property を書く費用がバグの費用を上回る

**否定する主張**: §66「property を書く負担が過度でない」、§3.2「既存 Common Lisp
プロジェクトへの段階的導入」。

**反証観測**: 既知の欠陥に対して、それを捕まえる property を書いて走らせるまでの手間が、
その欠陥を直接直す手間を超える。

**確認方法**: 下記「今日確認できること」の欠陥5件で実測する。

**発火時**: 既存コードベースには入らない。§44（LLM による property 生成）が
post-MVP ではなく**MVP の前提条件**に格上げされる。§65 の最初の矢印
（Source code → Specs / Properties）に設計を与えることが最優先になる。

**確認可能時期**: 今日。MCP は不要。

---

## F4. 最小反例が欠陥を指さない

**否定する主張**: §71 の問い5「失敗した最小反例は何か」、§16 shrinking。

**反証観測**: 縮小された反例を見ても、どこが悪いか分からない。技術的には失敗を示す値
だが、修正箇所を特定できない。

**確認方法**: 欠陥5件のうち property で捕まるものについて、**反例だけを見て**修正箇所を
特定できるかを試す。ソースを読まずに。

**発火時**: shrinking が動いていても価値が出ていない。property の粒度が粗すぎるか、
反例の提示形式が悪い。§14 の property-result のスキーマを見直す。

**確認可能時期**: 今日。MCP は不要。

---

## F5. `properties-for` に選択性がない

**否定する主張**: §66「修正後に関連 property だけ再実行可能」。

**反証観測**: 実運用で、`properties-for` が返すのが「全 property」か「ゼロ」かのどちらかに
寄る。中間が無い。

**確認方法**: 実プロジェクトに導入し、symbol あたりの関連 property 数の分布を見る。

**発火時**: 逆引き索引が機能していない。`:about` の粒度設計をやり直す。symbol 単位が
正しい単位なのかを含めて問い直す。

**確認可能時期**: property が一定数書かれた実プロジェクトが必要。MVP 単体では確認不可。

---

## F6. 契約の問いが発せられない

**否定する主張**: §71 の問い1・2（どの入力を受け入れるか / どの出力を返すべきか）が
LLM にとって重要である。

**反証観測**: `defspec-function` を実装して MCP に載せても、LLM がそれを問い合わせない。
あるいは問い合わせても、その後の編集内容が変わらない。

**確認方法**: transcript での呼び出し頻度と、返答が編集に影響したかを見る。

**発火時**: 5つの問いの選定が誤っている。LLM が実際に発する問いを観測し直し、問いの
集合を組み替える。**この条件のために、function spec は MCP より後に作る。**

**確認可能時期**: function spec と MCP の両方が揃った後。

---

## F7. 答えられない問いが繰り返し出る

**否定する主張**: 5つの問いが十分な集合である。

**反証観測**: LLM が同じ種類の情報を繰り返し求め、フレームワークがそれを持たない。

**確認方法**: transcript で、MCP が答えられなかった問い合わせを分類する。

**発火時**: 問いの集合に欠落がある。**これは発火してほしい条件**である。欠落が具体的に
特定できるので、5つの問いを6つに増やす根拠になる。

**確認可能時期**: MCP adapter 完成後。

---

## F8. check-it が交換不能

**否定する主張**: §66「check-it を交換可能」。

**反証観測**: 2つ目の backend を書こうとすると、backend の外で合意されている取り決め
（`run-generated-test` の返り値 plist の形、`compiled-generator` 構造体、`*size*` の
扱い方）が check-it 固有だと判明する。

**確認方法**: 素朴な網羅列挙 backend を1つ書いてみる。数時間で分かる。

**発火時**: 抽象が漏れている。§12 の generator backend protocol を引き直す。

**確認可能時期**: いつでも。ただし他より優先度は低い — 交換可能性は大目標ではなく
工学的な健全性の項目である。

## 今日確認できること

F3 と F4 は MCP を待たずに確認できる。しかも**証拠を集める必要がない**。

この MVP を構築する過程で、実在の Common Lisp コードの欠陥が実際に出た。記録済みで、
修正も判明していて、そして重要なことに、**cl-spec の有効性を問う前に集まった**ので
都合よく選ばれていない。

| 欠陥 | 内容 |
|---|---|
| `*size*` クランプ | check-it が数値上下限を `*size*` で丸め、`(range integer 20 100)` が 10 を生成 |
| `and` 畳み込みの参照漏れ | `reference-spec` を guard に落とし、`(and integer my-range)` がスタックを溢れさせた |
| 反例の浅いコピー | `list-of` 引数で shrink が元の反例を破壊 |
| `replay-property` の `:profile` 欠落 | 既定以外の profile で走った失敗を再現できず、静かに pass を返す |
| `list-of` の required-size 遅延 | 要素 generator を遅延させたため生成値が spec を満たさない |
| `invalid-property-form` の export 漏れ | 公開マクロが signal する condition を利用者が名指しできない |

各件について、事前に2つ問える。

1. **この欠陥は property で捕まえられたか。** 捕まえられるものと原理的に捕まえられない
   ものが分かれるはずで、**その境界が cl-spec の適用範囲そのもの**である。
2. **cl-spec を持つ LLM は、持たない LLM より速く見つけたか。**

1 は手を動かさずにできる。「どんな property なら捕まえたか」を書くだけである。
**書けないものが出てきたら、それが設計の限界**であり、MCP を作る前に知っておきたい。

なお現時点の見立てでは、`*size*` の件と `list-of` の件は §68 が自己 property として挙げて
いる「生成値は常に spec を満たす」で捕まる（実際、最終レビューはそれを指摘の根拠にした）。
一方 `invalid-property-form` の export 漏れは property では捕まらない。この差が境界である。

## 罠

**反証条件を書いたら、それが発火したときに本当に止まるかを今のうちに自問しておくこと。**
ここまで作った後だと「でもこれは条件が悪かっただけで」が必ず出る。この文書は、その一言
を封じるためだけに存在する。
